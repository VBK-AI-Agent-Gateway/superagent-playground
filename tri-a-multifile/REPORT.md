带 `[推断]` 的是基于仓库内代码快照的静态分析，需操作员在 EU 上用 `01-multi-file.sh` 的输出确认。

### P4 的缺陷与修复（值得记录）

第一版 `--apply` 把补丁体**插在**锚点行**之前**，锚点行及其原函数体全部保留 → 修补后的
`telegram.ts` 会出现**两份**函数体，产物语法错。这是一个「补丁脚本自己会把生产代码改坏」的
严重缺陷，且**只在真正 apply 时才暴露**。

修复：用 `awk` 做**整函数体替换**——匹配锚点后输出补丁体、置 `skipping`，丢弃原体直到证据
锚点 `evid` 出现。并加两道 fail-closed 门：

- 替换后锚文本次数必须 `== exp - 1 + 补丁体重写数`；
  **少 = 原体多删，多 = 原体没删干净（重复函数体）**，两种都中止；
- 形态门断言特征串真实落地。

这两道门在开发期**实际拦住了我自己两次错误**（第一次锚文本残留，第二次 `exp` 未在阶段二
重新读取导致期望值错误）——门不是摆设，这是它活着的证据。

## 二、根因

### 2.1 实测（本环境可复现）

`[实测]` **合成夹具往返验证**：构造与生产同形的三文件夹具，`--apply` → `15 PASS / 0 FAIL`，
补丁后 `telegram.ts` 含保序列表、`bot.ts` 双写两槽、`ws-sync-queue.ts` 逐条目 `mkdir -p`；
`--rollback --from <戳>` → 三文件**字节级还原**，特征串计数归零。

`[实测]` **门拦得住**：把 `exp` 改成错误值后重跑，G2' 门立刻 FAIL 并中止，未产生任何写入。

`[实测]` **空跑不误伤**：在本开发机直接跑（无 `/srv/wagate/patches`）→
`0 PASS / 3 FAIL`，明确报「文件不存在」，优雅降级而非中途崩。

### 2.2 推断（静态分析，待 `01-multi-file.sh` 现场确认）

`[推断]` **单槽黑板模式是主因**。earlier 版本的实际链路是：

1. `telegram.ts` 为每个 `update.message` 只保留一个局部 `let file`；
   多附件时循环里后一个覆盖前一个。
2. `bot.ts:218` 把该 `file` **赋值**给 `globalThis.__excelPendingFile`；
   第二次赋值直接覆盖第一次。
3. `tenant-core.ts:1224-1225` 的 `__pendingImage` / `__pendingImageSid` 同样是「最后一张胜出」，
   且仅以 `sid` 为键、命中即提前 return。
4. 仓库内约 15 个裸 `globalThis` 槽位共享同一模式 → 系统性风险，非单点 bug。

`[推断]` **叠加因素**：`telegram.ts:171-181` 对每个 update 做 fire-and-forget
`handleUpdate(update)`；`tenant-core.ts:1211` 用 `locks.get(sid)` 的 promise 链**串行化同一租户**、
跨租户并发。同租户内的多附件不会因锁而丢，**丢在更前面的单槽覆盖**，所以并发锁不是解药。

`[推断]` **坑 #14（静默丢文件）**：`ws-sync-queue.ts` flush 前若未建父目录，首次写入必失败；
若失败只是被 catch 掉而不告警，则表现为「文件凭空消失」。这是「不报错但丢数据」的典型。

> **必须强调**：`ws-sync-queue.ts`、`upload-ops`、`aa-voice` 这些源文件**在本仓库历史中不存在**，
> 只在 EU 主机上。本报告**绝不为它们引用仓库行号**；`01-multi-file.sh` 第 1、4 节负责在 EU 上
> 定位并导出真实内容，P3 补丁的锚点与变量名以那份输出为准。

### 2.3 实测与推断的分界

| 结论 | 状态 | 确认方式 |
| --- | --- | --- |
| 单槽覆盖是主因 | 推断 | `01-multi-file.sh` 第 2、3 节现场 grep 计数 |
| 补丁能正确落地且可回滚 | **实测** | 合成夹具 apply/rollback 往返 |
| 门能拦住错误补丁 | **实测** | 故意改错期望值，门 FAIL 中止 |
| 坑 #14 父目录缺失 | 推断 | `01-multi-file.sh` 第 4 节 |
| 修复后两文件都进沙箱 | **未验证** | 需 EU 上 `regr/regrA.sh`（本环境无凭据） |

## 三、修复映射

| 问题 | 修复 | 门 |
| --- | --- | --- |
| 单槽覆盖（telegram 局部 `file`） | 增加保序列表 `__fixAFileList__`，逐附件下载入列 | G3 入站计数日志 |
| 单槽覆盖（`__excelPendingFile`） | **双写**：列表槽保序保量 + 单槽写最后一个（旧消费方零改动） | G2 形态门 |
| 只冲最后一个 + 父目录缺失（坑 #14） | flush 前逐条目 `mkdir -p` | G2 形态门 `__fixAMkdir__` |
| 静默失败 | 任何门失败 → 告警日志 + 可选 TG，绝不静默 | `gate_fail` 唯一失败出口 |

**回退性**：改动是**原地替换 + 保留 `.bak`**，回滚是字节级还原；双写设计保证旧消费方
（只读单槽的那些）在补丁生效期间**行为不变**，因此回退窗口内无中间态风险。

## 四、复发预防表（issue #37 验收基调 ①：机械门，不靠人盯）

| 问题类别 | 哪个机械门阻止它 | 该门如何证明自己活着 |
| --- | --- | --- |
| 现场代码已变、锚点对不上 | **G1 锚点计数门**（期望次数断言） | 开发期把期望值改错 → 门 FAIL 并中止；现场 `--verify-gate` 全 PASS 才允许 apply |
| 补丁把原体插在前面 → 重复函数体 | **G2' 替换唯一性门** | 开发期真实触发过两次（残留锚文本 / `exp` 未刷新），均被拦下且零写入 |
| 补丁语法正确但逻辑没落地 | **G2 形态门**（特征串断言） | 补丁后 grep 特征串必须存在，缺则中止并提示回滚 |
| 多文件仍然丢（修复没生效） | **G3 N 进 N 出计数门** | 入站 `multi-file inbound n=` 与出站沙箱/台账计数必须相等 |
| 首写失败静默丢文件（坑 #14） | **父目录预建 + 失败告警** | `mkdir -p` 失败走 `console.error`，不再静默 |
| 回归复发（人眼看不出来） | **`regr/regrA.sh` 合成用例** | 一条命令复跑：2 个 xlsx 必须都到达沙箱；缺证据直接 FAIL，不假绿 |
| 失败无人知 | **通知**（日志 + 可选 TG） | `TG_NOTIFY!=1` 或凭据缺失时打印「未发 TG」并写日志，绝不静默 |
