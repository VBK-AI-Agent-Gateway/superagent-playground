## 0. 结论速览

| 问题 | 结论 |
|------|------|
| **Q1 技能包装哪** | **默认装 VM，不装 PI。** 只有「与 EU 本地数据/租户隐私强绑定，且必须在秒级前台交付」的岗位技能才留在 PI。判据是 **数据落点 × 交付时延 × 变更频率** 三轴，见 §2.1 |

## 1. 名词与现状基线

### 1.1 两套系统的本质差异

| 维度 | PI（EU wagate 容器内） | VM（superagent worker） |
|------|------------------------|--------------------------|
| 形态 | 多租户前台助手，TG 桥接 | 单机编码智能体，GitHub 工单驱动 |
| 技能机制 | **有**：`SKILL.md` + 11 岗位 100 技能 + skillGuide 索引注入 + `skill_read` 按需读 | **无对等机制**：行为靠 `prompts/` + `AGENTS.md` 塑造 |
| 工具面 | `sbx_*`（沙箱视图）+ 宿主插件（`skill_ls` / `skill_read` / `deliver_local` / `doc_pack` …） | `WORK_TOOLS`（**源码实测**，见 §1.2） |
| 数据可达 | 租户数据、私有文档（**不出 EU**） | 公开仓库、GitHub 工单（**无生产凭据**） |
| 交付时延 | 秒~分钟级本地交付 | 分钟~小时级 PR 交付 |
| 隔离 | 四层软隔离 + 暖池 + 任务级 `sbx-<id>` | 每工单独立 git worktree + 工具面 restrict |

### 1.2 VM 侧工具面（03 实测，`src/app/sessions.ts:61`）

```
WORK_TOOLS = ['read','write','edit','read_image','glob','grep','bash','pwsh',
  'job_output','job_list','job_kill','web_search','web_fetch','skill','todo_write',
  'subagent','list_subagent_models','send_message','list_agents','interrupt_agent']
```

**关键发现**：`skill` 工具**已经在 `WORK_TOOLS` 里**（03 实测）。也就是说 VM 侧并非「没有技能能力」，而是**只有通用 `skill` 工具，没有任何技能包内容与索引注入机制**——能力在，供给不在。这让 Q1 的「装 VM」比想象中便宜：**不需要新建工具，只需要建立技能内容 + 分发 + 注入**。

同时，`workOnly()`（`sessions.ts:292`）对 worker 做工具面 restrict：`interrupt_agent` / `send_message` 等保留，但**工具面是白名单制**——任何新工具都要显式进 `WORK_TOOLS` 才能被 worker 用到。

## 2. Q1：技能包落位决策规则

### 2.1 决策三轴（先答「哪类放哪」）

判据不是「哪种技术更好」，而是三个客观属性：

| 轴 | 问题 | 偏向 PI | 偏向 VM |
|----|------|---------|---------|
| **A 数据落点** | 技能要读的数据在哪？ | 租户私有数据、EU 本地文档 | 公开仓库、GitHub、公网 |
| **B 交付时延** | 期望多久出结果？ | 秒~分钟（前台对话） | 分钟~小时（PR 评审） |
| **C 变更频率** | 谁维护、多久改一次？ | 岗位知识、低频、业务方维护 | 工程 playbook、高频、工程方维护 |

**规则**：三轴中 **A 具一票否决权**（隐私红线不可交易）；A 不偏向时看 B；B 也不分伯仲时看 C（高频变更走 VM，因为 VM 侧有 git + PR + CI 全套版本化）。

### 2.2 分类裁决表（不做两面派）

| 技能类别 | 判断 | 落位 | 理由 |
|----------|------|------|------|
| **岗位技能**（sales / legal / data / productivity …，100 个） | A=私有数据，B=秒级 | **PI** | 三轴全偏 PI。已有机制成熟（索引注入 + 按需读 + 配额防穿越），**不要迁移** |
| **流程知识包**（跨系统 SOP、审批流、话术模板） | A 决定性 | **按数据落点二分**：涉及租户/私有数据 → PI；纯公开流程 → VM | 同一条 SOP 若两端都要，用 §3.3 的 registry 做**同源双分发**，不是复制两份 |
| **开发 playbook**（建站规范、代码风格、自检脚本、PR 模板） | A=公开代码，C=高频 | **VM** | 只对 VM 有意义；PI 不写代码。天然属于 git 版本化世界 |
| **模型/工具调用规范**（prompt 片段、函数签名约定） | 看消费方 | **跟随消费方** | PI 用的留 PI，worker 用的留 VM；若共用则 registry 管理 |

### 2.3 「默认装 VM，不装 PI」的含义澄清

速览里的「默认装 VM」指的是 **面向开发/工程类的增量**（这恰好是新增技能包的主要诉求）。**不等于**把现有 100 岗位技能从 PI 挪走——那会打破「个人数据不出 EU」红线，且 PI 侧机制已经工作良好。

### 2.4 落位到 VM 的可行性（03 实测支撑）

- `skill` 工具**已在 `WORK_TOOLS`** → 零新增工具面改动
- 缺的是：技能内容存放位置、索引注入点、worker 提示词里的使用引导
- 成本约束：磁盘 93%，技能包应**按需拉取/软链**，不做全量常驻副本

### 2.5 落位到 PI 的增量约束（待 01 补证）

- 新增技能要走 `/srv/wagate/skills` → 容器挂载，**宿主与容器一致性**需 01 的 md5 对比确认
- `skillGuide` 每轮注入索引：**技能数增长会线性抬高每轮 token**。100 → 200 之前必须先解决「索引分段/按岗位过滤」，否则前台成本与延迟都会劣化

## 3. Q2：数字AI员工架构设计

### 3.1 设计原则（对齐 `docs/000-philosophy.md`）

`000-philosophy.md` 的核心是 **「take as little human attention as possible」**，并明确 **Do not use it to produce volume**。因此「数字AI员工」不能理解成「多招几个 agent 多干活」，而应理解为：

> **一个能被信任、能被监督、能长期在岗、不制造噪音的『同事』。**

由此推导出四条设计约束：
1. **身份可辨**：每个员工有稳定身份，不是一次性脚本
2. **边界先行**：先划权限与红线，再谈能力
3. **人手注意力是稀缺资源**：默认沉默，只在有可用结果或必须决策时说话
4. **质量门是入职条件**：没有质量门的员工不许上岗

### 3.2 目标架构：三层 + 一个单一事实源

```
┌───────────────────── 控制面（EU，身份与数据所在）─────────────────────┐
│  • 员工身份 registry（谁是谁、属于哪个租户/岗位）                     │
│  • 技能 registry（单一事实源，git）                                    │
│  • 租户与权限边界（个人数据不出 EU）                                   │
│  • 计费与配额（永不做投机 LLM 计费）                                   │
└───────────────┬───────────────────────────────────────────────────────┘
                │  技能分发（同源双发）+ 工单派发（GitHub）
                ▼
┌───────────────────── 执行面（VM，通用算力）───────────────────────────┐
│  • orchestrator + per-ticket worker + subagent（maxWorkers=3）        │
│  • 质量门三件套：smoke.sh / sa-deliver.sh / sa-watchdog.sh            │
│  • 技能注入点：prompts/ + AGENTS.md + registry 拉取的技能包            │
│  • 红线：无生产凭据、无投机计费、fail-open                             │
└───────────────┬───────────────────────────────────────────────────────┘
                │  GitHub 工单（公开任务）
                ▼
┌───────────────────── 前台面（PI，EU 容器内）──────────────────────────┐
│  • 轻活本地交付（deliver_local，秒级，GitHub 零参与）                  │
│  • 岗位技能消费（skillGuide 索引 + skill_read）                        │
│  • 租户私有数据，不出 EU                                               │
└───────────────────────────────────────────────────────────────────────┘
```

**一句话**：**控制面留 EU，执行面给 VM，技能走 git 单一事实源同源分发。** 这正是既有「分轨决策（11-04）」的延续，只是把「技能包」这条此前缺失的线补上。

### 3.3 技能生命周期（从 M0 到 M2）

现状 M0：技能只存在于 PI 侧宿主目录，无 registry、无版本、无跨机分发。

**M1 目标：技能 registry + 统一安装接口**
- **单一事实源**：一个 git 仓库（或本仓库下一个 `skills/` 目录）存所有技能包
- **分发**：EU 侧同步脚本（宿主 `/srv/wagate/skills`）+ VM 侧拉取脚本
- **安装接口**：`install <skill-id> <target>`，target ∈ {pi, vm}
- **解决什么**：坑 #29「双目录双清单」的教训——**同一技能两边各一版会漂移**。M1 之后，任何技能的权威版本只有一个

**M2 目标：多租户岗位隔离**
- 租户级技能包（「每个客户配专属员工」）
- 技能 registry 支持租户维度过滤：`skillGuide` 只注入该租户岗位相关技能
- 同时解决 §2.5 的索引膨胀问题

### 3.4 调度与并发

- **现状（03 实测）**：`maxWorkers=3`，4 核 / 4.7G；工单驱动，无优先级队列
- **建议**：保持工单驱动（这是「按需上岗」的天然形态），不要引入常驻轮询式调度——那会违反「不做无人要求的活」原则
- **瓶颈判断**：11-05 咨询结论是「堆 VM 只解决并发数，真瓶颈=模型 API 账单 + TG/GitHub 平台限额」。03 实测的 4 核/4.7G 也印证：**单机纵向扩展已接近上限**（内存 free 仅 258Mi，靠 3.2G buff/cache 撑着）

### 3.5 质量门（Q2 的「入职条件」）

**复用现有三件套，不新造**（03 实测在位）：

| 门 | 时机 | 现有实现 |
|----|------|----------|
| 语法/加载门 | 交付前 | `smoke.sh` |
| 交付门 | 每 5 分钟 | `sa-deliver.sh`（smoke 不过 → HOLD，不上 Pages） |
| 监督门 | 每 5 分钟 | `sa-watchdog.sh`（600s FLAG / 900s stop） |

**待补强**：目前三道门都偏「工程正确性」，**缺「行为正确性」门**——即员工是否说了不该说的、是否越权。建议 M2 引入轻量行为审计（复用 PI 侧 `claw-billing` / Inngest 的监督思路），但**必须在数据缺口补齐后再定方案**。

### 3.6 监督

- EU 侧已有：`claw-billing` / `claw-newapi` / Inngest(8288) 做任务生命周期监督
- VM 侧已有：`sa-watchdog.sh` 做卡死检测
- **缺口**：两侧监督**不互通**。VM 员工卡死 EU 不知道，EU 租户异常 VM 不知道。M1 之后应有一个统一「员工状态」视图（但按 philosophy，**只在需要人介入时显示**，健康状态不占空间）

### 3.7 成本

- **红线（不得破坏）**：**永不投机 LLM 计费**。所有模型调用必须由真实用户意图触发
- **现状**：三角色（大脑/worker/eval）均为 DeepSeek-V4.1-Flash，经笔记本模型桥 `192.168.58.1:8767`（VM 无模型 key）
- **优化方向**：角色分模型——判官/分诊用快模型（EU 侧已有 `GLM-5.3-Flash`、`gemma4:12b` 等白名单），重活才用主力模型。这一条**必须在 02 实测出各模型延迟与单价后再定阈值**

### 3.8 演进路径（里程碑 + 触发条件）

> 原则：**没有触发条件就不许堆里程碑**。

| 里程碑 | 内容 | **触发条件** |
|--------|------|--------------|
| **M0 = 现状** | PI 技能 + VM 工单，两套独立 | — |
| **M1** | 技能 registry + 统一安装接口 + 同源双分发 | **触发**：出现第一个「PI 与 VM 都需要」的流程知识包；或 01 实测确认宿主/容器技能目录已漂移 |
| **M2** | 多租户岗位隔离（租户级技能包 + 索引过滤） | **触发**：第二个租户要求独立技能集；或 `skillGuide` 索引导致每轮 token 明显劣化（01 需给出实测 token 数） |
| **M3** | VM 集群水平扩展（VM 纯算力，控制面留 EU） | **触发**：`maxWorkers=3` 持续打满且工单排队成为常态；**且**模型账单/平台限额已不是瓶颈 |

### 3.9 红线（沿用既有决策，不得破坏）

1. **永不投机 LLM 计费**（计费红线）
2. **个人数据不出 EU**（隐私红线）——这条直接决定 §2.1 的 A 轴一票否决
3. **fail-open**
4. **worker 无生产凭据**（爆炸半径控制）
5. **补丁循环 = 架构债**——delivery-hub 教训：路径多了就改结构性单一事实源，**不再堆开关**
